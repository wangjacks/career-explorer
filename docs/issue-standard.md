# Issue 编写标准规范

本文档定义本项目 GitHub Issue 的标题、标签、正文和验收标准，供所有协作者和 Agent 遵循。

## 1. 标题格式

标题只描述**问题或结果**，读一眼能判断验收对象。类型、优先级、领域与版本不写入标题，由 GitHub 原生字段表达：

| 信息 | 承载位置 |
|---|---|
| 类型 | `type:*` Label |
| 优先级 | `priority:*` Label（或 Projects 的 Priority 字段） |
| 业务领域 | `area:*` Label |
| 版本 | Milestone |
| 依赖与拆分 | blocked-by / blocking / sub-issues |

**写作规则：**

- 使用具体、可验证的描述，避免「优化」「改进」「问题」「调研一下」等模糊词。
- Bug 写「触发条件 + 现象」，Feature 写「能力 + 结果」，Refactor 写「改什么、外部行为不变」，Docs 写「补哪份文档的什么缺口」。
- 建议不超过 70 个字符（列表截断的常见安全线，并非平台硬限制），不加尾句号，不使用 emoji。
- 不使用 `[P1]`、`[P1-B]`、`[feat]`、`[bug]` 等分类前缀；Issue 编号（`#123`）已经是稳定标识，标题不承载排序或筛选语义。
- 允许可选的**组件前缀**，仅用于消歧，格式为 `组件：结果`，例如 `统计：同名班级在趋势图被合并`。组件前缀表达归属，不表达优先级或类型。

**标题示例：**

- Feature：`支持腾讯云 COS 与阿里云 OSS 对象存储`
- Bug：`登录页在会话 Cookie 损坏时返回 500`
- Refactor：`把管理面板 Tab 拆成独立路由`
- Docs：`补充演示环境的两条数据生成路径`

优先级调整、领域变更或版本迁移都不需要修改标题；Issue 类型通过 Label 表达，不写入标题。

## 2. Labels

创建 Issue 时至少添加一个 `type:*` 标签；需要排期时同时添加 `priority:*`；涉及明确业务领域时添加 `area:*`。

### 类型标签

| Label | 用途 |
|---|---|
| `type:feature` | 新功能或产品需求 |
| `type:bug` | 功能异常或错误 |
| `type:refactor` | 不改变外部行为的代码重构 |
| `type:security` | 安全修复和安全加固 |
| `type:perf` | 性能优化 |
| `type:docs` | 文档改进 |
| `type:question` | 需要讨论或补充信息 |

一个 Issue 可以同时使用多个类型标签，例如安全相关的重构可以使用 `type:refactor` + `type:security`。

### 优先级标签

| Label | 用途 |
|---|---|
| `priority:P0` | 阻塞性问题或严重风险 |
| `priority:P1` | 当前迭代必须完成 |
| `priority:P2` | 重要但可以延后 |
| `priority:P3` | 后续规划或体验优化 |

### 领域标签

| Label | 用途 |
|---|---|
| `area:student` | 学生端、表单、档案、学生面板 |
| `area:admin` | 管理员/教师面板、管理、导入导出、统计 |
| `area:auth` | 激活、登录、认证和权限 |
| `area:tag` | 标签体系 |

### 其他仓库标签

以下标签按场景使用：`dependencies`、`javascript`、`duplicate`、`invalid`、`wontfix`。

不要创建与仓库现有标签含义重复的新标签；如果标签体系发生变化，应先同步修改本文档。

## 3. Milestone

纳入版本迭代的 Issue 必须加入对应 Milestone，例如 `v2.0.0`。纯讨论或尚未确定版本的规划 Issue 可以暂不指定 Milestone，但应在正文中说明预期阶段。

当前主要 Milestone：

- `v2.0.0`：当前版本收官和正式发布

## 4. Body 结构

### 4.1 背景

所有功能 Issue 必须说明为什么要做，包含需求来源、用户价值或当前风险。

```markdown
## 背景

当前系统将用户文件保存到应用服务器本地。随着访问规模增加，本地存储和带宽会成为部署风险，因此需要支持对象存储。
```

### 4.2 现状

Bug Issue 必须包含现状、相关文件和复现步骤。Feature Issue 可以改用“实现目标”。

### 4.3 实现目标或修复方案

Feature 使用 `## 实现目标`，说明期望行为、API、数据模型、目录规划和技术边界。

Bug 使用 `## 修复方案`，说明修改方向、根因和关键实现思路。

### 4.4 涉及文件

推荐列出至少一个涉及文件或目录，并说明其职责。尚未确定的文件可以列出预计修改位置，不要为了凑数量虚构文件。

```markdown
## 涉及文件

- `src/lib/db.ts` — 数据访问接口
- `src/app/api/manage/example/route.ts` — 管理端 API
```

### 4.5 验收标准

必须使用可验证的 checkbox，并覆盖功能、权限、异常情况和测试要求。

```markdown
## 验收标准

- [ ] 正常流程符合预期
- [ ] 未授权请求被正确拒绝
- [ ] 失败场景有明确错误提示
- [ ] 补充相关单元测试
- [ ] `npm run lint` + `npm run build` 全绿
```

所有 Issue 的验收标准必须包含 `npm run lint` + `npm run build`。涉及逻辑变更时，应同时要求 `npm test` 或对应集成测试通过。

### 4.6 关联

说明所属 Roadmap、依赖的 Issue、配套功能或后续阶段。没有关联项时可以写“无”。

## 5. 类型模板

### Feature

```markdown
## 背景

（为什么需要该功能）

## 实现目标

（期望行为、API、数据模型和技术边界）

## 涉及文件

- `path/to/file` — 职责说明

## 验收标准

- [ ] （具体可验证条件）
- [ ] `npm run lint` + `npm run build` 全绿

## 关联

- （Milestone、依赖或配套 Issue）
```

### Bug

正文结构为：背景 → 现状（含复现步骤）→ 修复方案 → 涉及文件 → 验收标准 → 关联。

### Refactor

正文结构为：背景 → 现状 → 重构方案 → 涉及文件 → 验收标准 → 关联，并明确不改变的外部行为。

### Security

正文结构为：背景 → 风险描述（含攻击向量）→ 修复方案 → 涉及文件 → 验收标准 → 关联。必要时同时添加 `type:bug` 或 `type:refactor`。

### Question

说明背景、当前已知信息和需要决策的问题。若讨论结束后形成开发任务，应新建或转换为带有 `type:feature` 的 Issue。

## 6. 脱敏要求

Issue 正文不得包含：

- 服务器 IP、域名、账号、密码、Token、密钥或私钥
- 真实学生、教师或管理员的个人信息
- 生产数据库连接信息
- 未公开的内部会议链接或附件内容

可以保留经过概括的用户规模、部署约束、技术方案和性能目标，但不能通过组合信息反推出具体生产环境。

## 7. 创建前检查

- [ ] 标题描述问题或结果，不含优先级、领域、类型前缀（需要时只用可选的组件前缀）
- [ ] 已添加正确的 `type:*` 标签
- [ ] 已按需要添加 `priority:*` 和 `area:*` 标签
- [ ] 已加入对应 Milestone，或说明为何暂不加入
- [ ] Feature 包含「背景」「实现目标」「验收标准」
- [ ] Bug 包含「背景」「现状」「修复方案」「验收标准」
- [ ] 涉及文件和验收条件具体、可验证
- [ ] 已完成敏感信息脱敏
